# 1. Корректность данных

## 🔴 B1. Каскад rollup портит часовые и дневные агрегаты

**Файл:** `collector/index.mjs:1332-1362` (`rollupLevel`), `:1288-1316` (`rollupRange`)

`rollupLevel` сворачивает «свежий хвост» так:

```js
const tailLo = new Date(Math.max(srcLo.getTime(), srcHi.getTime() - tail * step));
let written = await rollupRange(..., tailLo, new Date(srcHi.getTime() + step));
```

`srcHi` — это `MAX(bucket)` источника, то есть **произвольная минута** (например
`14:37`), а `step` — час. Значит `tailLo = 08:37`, и диапазон свёртки —
`[08:37, 15:37)`. Внутри `rollupRange` идёт `GROUP BY date_trunc('hour', bucket)`,
поэтому час `08:00` считается **только по минутам 37–59**, а записывается
`ON CONFLICT DO UPDATE SET volSum = EXCLUDED.volSum` — то есть **перезаписывает**
ранее посчитанное полное значение обрезком.

Каскад крутится раз в 5 минут. Пока `srcHi` идёт по часу `[H+6h, H+7h)`, час `H`
переписывается 12 раз, каждый раз меньшим куском. Потом `H` выпадает из окна
хвоста, а обратный проход по истории идёт от `MIN(bucket)` назад и до него уже
не доходит — **обрезок остаётся навсегда**.

**Подтверждено на живой базе.** Сверка `ObRollupBucketH` с суммой по
`ObRollupBucket` за тот же час:

```
 symbol  |    exchange     |         bucket         | written | snaps_true | pct
---------+-----------------+------------------------+---------+------------+------
 BTCUSDT | binance-futures | 2026-08-28 22:00:00+00 |    1135 |       1195 | 95.0   ← прямо сейчас режется
 ETHUSDT | binance-futures | 2026-08-25 15:00:00+00 |     134 |       3466 |  3.9   ← замёрзло навсегда
 BTCUSDT | binance-futures | 2026-08-24 14:00:00+00 |     539 |       3450 | 15.6
 ETHUSDT | binance-futures | 2026-08-17 20:00:00+00 |     299 |       3102 |  9.6
```

Сводно: часовой уровень — 15 из 518 часов битые, в среднем сохранено 34.8%,
худший случай 3.9%. **Дневной уровень — 7 из 55 суток битых, худший 16.7%**
(механизм тот же: хвост 2 суток, а граница — произвольный час).

> Поправка к первой редакции отчёта: цифру по суткам я сперва снял запросом,
> в котором в `ON` не было `symbol`/`exchange` — выходило перекрёстное
> соединение и завышенное число строк («16 из 69»). Верные цифры и запрос —
> здесь и в разделе 8. По часам запрос был корректен, те числа в силе.

Час `2026-08-28 22:00` на 95% — это тот самый час, по которому граница ползёт
сейчас; он доедет до нескольких процентов и застынет.

**Почему это не бросается в глаза.** Яркость карты считается как
`volSum × ex / snaps`, и `snaps` режется тем же диапазоном — деление скрывает
масштаб потери. Но смысл всё равно ломается: часовой бакет перестаёт быть
СРЕДНИМ стаканом за час и становится снимком случайных 1–3 минут. Стена,
простоявшая 55 минут из 60, с карты исчезает, если не попала в выборку.
На 1h/4h/12h/1d/1w карта ордеров рисуется именно из этих таблиц.

**Как проверить у себя:**

```sql
WITH cmp AS (
 SELECT h.symbol, h.exchange, h.bucket, h.snaps AS written, src.snaps_true
 FROM "ObRollupBucketH" h
 JOIN (SELECT symbol, exchange, date_trunc('hour', bucket) hr, SUM(snaps) snaps_true
       FROM "ObRollupBucket" GROUP BY 1,2,3) src
   ON src.symbol = h.symbol AND src.exchange = h.exchange AND src.hr = h.bucket
      -- текущий час ещё набирается: минутный слой уходит вперёд между
      -- прогонами каскада (раз в 5 минут), и без этого условия он всегда
      -- выглядит «обрезанным» на несколько процентов
      AND src.hr < date_trunc('hour', now()))
SELECT count(*) AS hours, count(*) FILTER (WHERE written < snaps_true) AS broken,
       min(round(100.0*written/NULLIF(snaps_true,0),1)) AS worst_pct
FROM cmp;
```

**Как исправить.** Границы диапазона обязаны лежать на границе целевой единицы —
ровно так, как уже сделано в `rollupFootprintLevel` (`date_trunc('hour', $1)`).
Правка в `rollupLevel`:

```js
// Границы округляем ВНИЗ до целевой единицы: иначе крайний период
// сворачивается по куску и ON CONFLICT DO UPDATE затирает им полное значение.
const floorTo = (ms) => Math.floor(ms / step) * step;

const rawTailLo = Math.max(srcLo.getTime(), srcHi.getTime() - tail * step);
const tailLo = new Date(floorTo(rawTailLo));
let written = await rollupRange(
  srcPrices, dstPrices, srcSnaps, dstSnaps, unit,
  tailLo, new Date(floorTo(srcHi.getTime()) + step),
);

const dstLo = rows[0]?.dst_lo ? new Date(rows[0].dst_lo) : tailLo;
if (dstLo.getTime() > srcLo.getTime()) {
  const histLo = new Date(floorTo(Math.max(srcLo.getTime(), dstLo.getTime() - chunk * step)));
  written += await rollupRange(srcPrices, dstPrices, srcSnaps, dstSnaps, unit, histLo, dstLo);
}
```

`floorTo` для суток корректен: `date_trunc('day')` в UTC совпадает с кратностью
86 400 000 мс.

**Разовое лечение уже испорченного** (после выката правки):

```sql
-- часовой уровень
INSERT INTO "ObSnapshotRollupH" ("symbol","exchange","bucket","price","volSum","bidSum","askSum")
SELECT symbol, exchange, date_trunc('hour', bucket), price,
       SUM("volSum"), SUM("bidSum"), SUM("askSum")
```

Часы старше `ROLLUP_MINUTE_RETENTION_DAYS` (30 дней) восстановить нечем —

## 🔴 B2. `flushRollup` теряет накопленную минуту при любой ошибке записи

**Файл:** `collector/index.mjs:584` (`fpRollup.delete`), `:614` (`tradeRollup.delete`), `:640` (`rollup.delete`)

```js
for (const [key, e] of rollup) {
  if (e.bucketMs >= curBucket) continue;
  rollup.delete(key);          // ← удаление ДО попытки записи
  ...
  try { await pool.query(...) } catch (err) { console.error(...) }   // ← упало — данные уже потеряны
}
```

Любая транзиентная ошибка (рестарт БД по watchtower, deadlock, `lock_timeout`
во время `pruneOld`, OOM backend'а) молча съедает целую минуту стакана, ленты и
футпринта по всем фидам. Восстановить нечем: rollup — единственный носитель
истории лимиток, сырой `ObSnapshot` живёт 7 дней и всё равно уже прочитан.

Проблема известна — она прямо описана в комментарии к миграции
`20260817210000_orderflow_index_diet` как причина не создавать индексы обычным
`CREATE INDEX`. То есть архитектура подстраивается под баг вместо того, чтобы
его чинить.

**Как исправить** — удалять из памяти только после успешной записи, а при сбое
оставлять бакет на следующий проход (upsert идемпотентен по сложению, но
повторная запись того же бакета удвоила бы суммы — поэтому нужен флаг «уже
пыталась»):

```js
for (const [key, e] of rollup) {
  if (e.bucketMs >= curBucket) continue;
  if (e.snaps === 0 || e.prices.size === 0) { rollup.delete(key); continue; }
  try {
    await writeRollupBucket(e);   // обе вставки внутри ОДНОЙ транзакции, см. B6
    rollup.delete(key);           // ← только после успеха
  } catch (err) {
    e.failures = (e.failures ?? 0) + 1;
    console.error(`[rollup] flush ошибка ${key} (попытка ${e.failures}): ${err.message}`);
    // после N неудач сдаёмся, чтобы память не росла бесконечно
    if (e.failures >= 5) rollup.delete(key);
  }
}
```

## 🟠 B3. Нет защиты от наложения `writeSnapshot`

**Файл:** `collector/index.mjs:1536`

```js
const writeTimer = setInterval(writeSnapshot, cfg.snapshotMs);   // 2000 мс
```

`writeSnapshot` — асинхронная и внутри делает: N последовательных upsert'ов
`ObLatestBook` (по одному на фид), четыре многострочных INSERT и `await flushRollup(t)`.
Если БД тормозит (идёт `VACUUM`, `pruneOld`, каскад), проход не укладывается
в 2 секунды и запускается следующий поверх. Дальше — лавина: пул `pg.Pool`
ограничен `max: 4`, вызовы встают в очередь, отставание растёт.

Все остальные периодические задачи коллектора такой guard имеют
(`candlesRunning`, `pruneBusy`, `vacuumBusy`, `allPairsScanRunning`) — этот
единственный забыли.

```js
let writeBusy = false;
async function writeSnapshot() {
  if (writeBusy) { console.warn("[write] предыдущий проход ещё идёт — пропускаем тик"); return; }
  writeBusy = true;
  try { /* ...текущее тело... */ } finally { writeBusy = false; }
}
```

## 🟠 B4. Многострочные INSERT без чанков — упрутся в лимит параметров Postgres

**Файлы:** `collector/index.mjs:738` (`ObSnapshot`), `:781` (`ObTrade`), `:801` (`ObFootprint`), `:820` (`ObBigTrade`), `:594` (`ObFootprintRollup`), `:648` (`ObSnapshotRollup`)

Все они строят один запрос с `rows.length × 6..7` параметрами. Протокол Postgres
ограничен **65 535** параметрами на запрос, то есть ~10 900 строк для 6 колонок.

Сейчас это не срабатывает, потому что уровней немного. Но `CollectorConfig.collectAll`
(тумблер «Отбирать всё» в админке) снимает порог `minCoins` — и число уровней
на фид вырастает на порядки. Достаточно включить его на паре символов с мелким
`BIN_SIZE`, чтобы получить `bind message supplies N parameters, but prepared
statement requires ...` и **полную остановку записи стакана** до выключения
тумблера. Тумблер при этом сам себя предупреждением не сопровождает.

```js
const MAX_PARAMS = 60000;
async function insertChunked(table, cols, rows) {
  const perRow = cols.length;
  const chunk = Math.max(1, Math.floor(MAX_PARAMS / perRow));
  for (let i = 0; i < rows.length; i += chunk) {
    const slice = rows.slice(i, i + chunk);
    const values = slice.map((_, j) =>
      `(${cols.map((__, k) => `$${j * perRow + k + 1}`).join(",")})`).join(",");
    await pool.query(
      `INSERT INTO "${table}" (${cols.map(c => `"${c}"`).join(",")}) VALUES ${values}`,
      slice.flat(),
    );
  }
}
```

То же касается `prisma.trade.createMany` в `src/lib/analytics/materialize.ts:70,92`:
у модели `Trade` 20 колонок → потолок ~3200 сделок за вызов. Аккаунт с большей
историей упрётся при полной пересборке.

## 🟡 B5. `flushRollup` вызывается вдвое чаще, чем задумано

**Файл:** `collector/index.mjs:827` (внутри `writeSnapshot`) и `:772` (`startRollupFlushBeat`)

## 🔴 S2. Все rate-limit обходятся одним заголовком

**Файлы:** `src/lib/ratelimit.ts:40-48`, `src/lib/traffic/hit.ts:113-117`, `deploy/nginx/nginx.conf`

```ts
export function clientIp(req: Request): string {
  const cf = req.headers.get("cf-connecting-ip");   // ← полностью под контролем клиента
  if (cf) return cf.trim();
  const xff = req.headers.get("x-forwarded-for");
  if (xff) return xff.split(",")[0].trim();          // ← первый элемент = то, что прислал клиент
  ...
}
```

Публичный вход — Tailscale Funnel → nginx. nginx ставит
`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` (**дописывает** к
присланному клиентом) и **никак не трогает `cf-connecting-ip`**. Cloudflare,
который эти заголовки нормализует, в схеме нет.

Итого достаточно `curl -H 'cf-connecting-ip: 1.2.3.4' ...` со случайным
значением на каждый запрос, чтобы обойти:

- `register:${ip}` — 5 регистраций / 15 мин → неограниченное создание аккаунтов
  (капча Turnstile опциональна: без `TURNSTILE_SECRET` `verifyTurnstile` просто
  пропускает);
- `login:${ip}` — 5/15 мин (остаётся ключ по email 10/час — это спасает от
  подбора пароля к КОНКРЕТНОМУ аккаунту, но не от password spraying по многим);
- `2fa:${ip}`, `gdrive-connect:*`, лимиты поддержки и загрузки картинок;
- `floodCheck(hit.visitorId)` в аналитике — `visitorId` считается как хэш
  IP+UA, то есть тоже управляем → залив `PageView` (самая быстрорастущая
  таблица) без ограничений;
- `verifyTurnstile(token, ip)` получает подделанный IP.

**Исправление в два слоя.**

nginx — перестать доверять клиенту (`deploy/nginx/nginx.conf`, во всех четырёх
`location`):

```nginx
proxy_set_header X-Forwarded-For $remote_addr;   # ЗАМЕНА, а не $proxy_add_x_forwarded_for
proxy_set_header CF-Connecting-IP "";            # снять подделку
proxy_set_header X-Real-IP $remote_addr;
```

Приложение — брать адрес из доверенного источника:

```ts
export function clientIp(req: Request): string {
  // За нашим nginx X-Real-IP/X-Forwarded-For выставляет прокси и затирает
  // присланное клиентом. CF-Connecting-IP читаем ТОЛЬКО если явно объявлено,
  // что перед нами Cloudflare.
  if (process.env.TRUST_CF_HEADERS === "1") {
    const cf = req.headers.get("cf-connecting-ip");
    if (cf) return cf.trim();
  }
  const real = req.headers.get("x-real-ip");
  if (real) return real.trim();
  const xff = req.headers.get("x-forwarded-for");
  if (xff) {
    const parts = xff.split(",").map((s) => s.trim()).filter(Boolean);
    return parts[parts.length - 1] || "unknown";   // ближайший к нам, а не самый дальний
  }
  return "unknown";
}
```

Дополнительно стоит поставить в nginx нижний рубеж, независимый от приложения:

```nginx
limit_req_zone $binary_remote_addr zone=auth:10m rate=10r/m;
location /api/auth { limit_req zone=auth burst=5 nodelay; ... }
```

## 🟠 S3. Отравление Host-заголовка → XSS в JSON-LD и порча robots/sitemap

**Файлы:** `src/lib/siteUrl.ts:16`, `src/app/layout.tsx:47`, `src/lib/seo.ts:104-117`

```ts
const host = h.get("x-forwarded-host") || h.get("host") || "localhost:3000";
return `${local ? "http" : "https"}://${host}`;
```

Хост принимается как есть и попадает в `siteJsonLd()`, который рендерится так:

```tsx
<script type="application/ld+json" dangerouslySetInnerHTML={{ __html: jsonLd }} />
```

`JSON.stringify` **не экранирует** `<`, `>` и `/`. Значение вида
`a"}</script><script>alert(1)</script>` в `x-forwarded-host` разрывает тег и
исполняется — CSP этому не мешает, потому что в политике стоит
`script-src 'self' 'unsafe-inline'`.

Браузер такой заголовок сам не пошлёт, так что это не прямой web-атакующий
вектор. Но: (а) любой промежуточный кэш/прокси превращает это в отравление кэша
для всех посетителей; (б) тот же `siteUrl()` питает `app/robots.ts` и
`app/sitemap.ts` — подставленный хост уводит поисковик на чужой домен.

**Исправление.** Экранировать при вставке в `<script>`:

```ts
const safeJsonLd = jsonLd.replace(/</g, "\\u003c").replace(/>/g, "\\u003e").replace(/&/g, "\\u0026");
```

И валидировать хост:

```ts
const HOST_RE = /^[a-z0-9.-]+(:\d+)?$/i;
const raw = h.get("x-forwarded-host") || h.get("host") || "localhost:3000";
const host = HOST_RE.test(raw) ? raw : "localhost:3000";
```

Ещё надёжнее — задать `SITE_URL` в проде явно (код это уже поддерживает и
предпочитает переменной окружения).

## 🟠 D1. 61 МБ дублирующих индексов — данные меньше, чем индексы

```
          tbl          |  total  |  heap  |   idx   |  rows
-----------------------+---------+--------+---------+--------
 ObCandle              | 211 MB  | 96 MB  | 115 MB  | 845876
 FxCandle              | 51 MB   | 24 MB  | 27 MB   | 243655
```

Причина — точные дубли первичных ключей:

| Индекс | Размер | Сканов | Дублирует |
|---|---|---|---|
| `ObCandle_symbol_exchange_interval_t_idx` | **49 MB** | 52935 | `ObCandle_pkey` (те же 4 колонки, тот же порядок) |
| `FxCandle_symbol_exchange_interval_t_idx` | **12 MB** | 90776 | `FxCandle_pkey` |
| `FxQuote_symbol_exchange_t_idx` | 8 kB | 0 | `FxQuote_pkey` |
| `FxDepthRollup_symbol_exchange_bucket_idx` | 8 kB | 0 | префикс `FxDepthRollup_pkey` |

Сканы у дублей ненулевые только потому, что планировщик выбирает любой из двух
одинаковых — после удаления всё уйдёт в PK.

Это ровно те индексы, которые миграция `20260817210000_orderflow_index_diet`
вычистила у `Ob*Rollup`, но у таблиц свечей не тронула. В схеме они объявлены
явно: `prisma/schema.prisma:389` (`ObCandle`), `:857` (`FxCandle`), `:889` (`FxQuote`),
`:911` (`FxDepthRollup`).

**Правка схемы** — убрать четыре строки `@@index`, дублирующие `@@id`:

```prisma
model ObCandle {
  ...
  @@id([symbol, exchange, interval, t])
  // @@index([symbol, exchange, interval, t])  ← удалить: точный дубль PK
  @@index([interval, symbol])
  @@index([t])
}
```

**Миграция:**

```sql
DROP INDEX CONCURRENTLY IF EXISTS "ObCandle_symbol_exchange_interval_t_idx";
DROP INDEX CONCURRENTLY IF EXISTS "FxCandle_symbol_exchange_interval_t_idx";
DROP INDEX CONCURRENTLY IF EXISTS "FxQuote_symbol_exchange_t_idx";
DROP INDEX CONCURRENTLY IF EXISTS "FxDepthRollup_symbol_exchange_bucket_idx";
```

`CONCURRENTLY` нельзя внутри транзакции Prisma-миграции — либо выполнить руками
на сервере, либо (эти индексы не под нагрузкой чтения) обычным `DROP INDEX`:
он берёт короткий `ACCESS EXCLUSIVE`, для `DROP` это миллисекунды.

**Эффект:** −61 МБ локально (пропорционально больше на проде), минус один
индексный write на каждую свечу. `ObCandle` переписывается каждую минуту по всем
символам и таймфреймам — это самая частая запись после стакана.

## 🟠 D2. Неиспользуемые первичные ключи на четырёх самых горячих таблицах

Схема утверждает (`prisma/schema.prisma:337-341`):

> в БД таблица партиционирована по дням … и **НЕ имеет PK** — `@id` здесь только
> для типизации клиента Prisma

Фактически PK есть на каждой партиции:

```
 ObSnapshot_p20260828_pkey                | 1800 kB | idx_scan = 0   (heap 5248 kB!)
 ObFootprint_p20260827_pkey               | 1040 kB | idx_scan = 0
 ObTrade_p20260826_pkey                   |  936 kB | idx_scan = 0
 ObBigTrade_p20260827_pkey                |   80 kB | idx_scan = 0
```

`idx_scan = 0` **по всем партициям без исключения** — ни один запрос в коде не
ищет по `id`. И сиквенсы живы:

```
 ObSnapshot_id_seq  | 1264574
 ObFootprint_id_seq |  763517
 ObTrade_id_seq     |  692281
```

Каждая записанная строка стакана/ленты/футпринта платит за `nextval` и вставку
в индекс, который никогда не читают. На партиции `ObSnapshot_p20260828` это
1800 кБ индекса при 5248 кБ данных — **34% лишнего объёма**.

**Как исправить.** Prisma требует уникальное поле в модели, но не требует, чтобы
оно было PK в БД — именно это и утверждает комментарий. Снять PK и сиквенс:

```sql
ALTER TABLE "ObSnapshot"  DROP CONSTRAINT IF EXISTS "ObSnapshot_pkey";
ALTER TABLE "ObTrade"     DROP CONSTRAINT IF EXISTS "ObTrade_pkey";
ALTER TABLE "ObFootprint" DROP CONSTRAINT IF EXISTS "ObFootprint_pkey";
ALTER TABLE "ObBigTrade"  DROP CONSTRAINT IF EXISTS "ObBigTrade_pkey";
-- на партиционированной таблице DROP CONSTRAINT каскадом снимает его и с партиций

ALTER TABLE "ObSnapshot"  ALTER COLUMN "id" DROP DEFAULT;
ALTER TABLE "ObTrade"     ALTER COLUMN "id" DROP DEFAULT;
ALTER TABLE "ObFootprint" ALTER COLUMN "id" DROP DEFAULT;
```

## 🟠 D3. Каскад дважды сканирует всю таблицу минутного rollup — каждые 5 минут

**Файл:** `collector/index.mjs:1334-1338`

```js
const { rows } = await pool.query(
  `SELECT (SELECT MIN("bucket") FROM "${srcPrices}") AS src_lo,
          (SELECT MAX("bucket") FROM "${srcPrices}") AS src_hi,
          (SELECT MIN("bucket") FROM "${dstPrices}") AS dst_lo`,
);
```

Миграция `orderflow_index_diet` заменила btree по `bucket` на BRIN. BRIN
обслуживает диапазонный `DELETE` в `pruneOld`, но **не умеет отвечать на
MIN/MAX** — планировщик уходит в Seq Scan:

```
 InitPlan 1 → Aggregate → Seq Scan on "ObSnapshotRollup"  (rows=16365)
 InitPlan 2 → Aggregate → Seq Scan on "ObSnapshotRollup"  (rows=16365)
 InitPlan 3 → Aggregate → Seq Scan on "ObSnapshotRollupH" (rows=1302)
```

Подтверждается статистикой: `ObSnapshotRollup` — **369 seq-сканов, 4.7 млн
прочитанных строк**; `ObRollupBucket` — 225 сканов / 1.58 млн;
`ObFootprintRollup` — 168 / 1.2 млн; `ObSnapshotRollupH` — 680 / 798 тыс.

Локально это 6 мс. На проде `ObSnapshotRollup` — самая тяжёлая таблица базы
(~0.22 ГБ в сутки × 30 дней ретеншна ≈ **6–7 ГБ**), и её полный проход дважды
каждые 5 минут на мини-ПК с одним диском вытесняет из `shared_buffers` всё
остальное.

**Исправление без единого нового индекса.** Границы времени идентичны у таблицы
цен и у парной таблицы счётчиков, а последняя в ~100 раз меньше (одна строка на
бакет вместо сотни):

```js
const { rows } = await pool.query(
  // MIN/MAX берём у таблицы СЧЁТЧИКОВ: диапазон бакетов у неё тот же, а строк
  // на два порядка меньше. По таблице цен это Seq Scan на гигабайты —
  // btree по bucket там снят намеренно (BRIN не отвечает на MIN/MAX).
  `SELECT (SELECT MIN("bucket") FROM "${srcSnaps}") AS src_lo,
          (SELECT MAX("bucket") FROM "${srcSnaps}") AS src_hi,
          (SELECT MIN("bucket") FROM "${dstSnaps}") AS dst_lo`,
);
```

`ObRollupBucket` тоже без btree по `bucket`, но её seq-скан — это 7.5 тыс. строк
вместо 16 тыс.×N цен, разница на порядки. Если и этого много — добавить
`@@index([bucket])` **только** на таблицы счётчиков (`ObRollupBucket`,
`ObRollupBucketH`, `ObRollupBucketD`): они маленькие, индекс дешёвый.

То же самое в `rollupFootprintLevel` (`collector/index.mjs:1369-1373`) —
`MAX(bucket) FROM ObFootprintRollupH` и `MIN(bucket) FROM ObFootprintRollup`
идут по таблицам цен. У футпринта парной таблицы счётчиков нет, поэтому здесь
нужен именно индекс:

```sql
CREATE INDEX CONCURRENTLY "ObFootprintRollup_bucket_btree"  ON "ObFootprintRollup"  ("bucket");
CREATE INDEX CONCURRENTLY "ObFootprintRollupH_bucket_btree" ON "ObFootprintRollupH" ("bucket");
```

(создавать из коллектора через `ensureRollupIndexes`, как уже сделано с BRIN —
`CREATE INDEX` в транзакции Prisma-миграции заблокирует вставки).

## 🟠 D4. Админка коллектора — самая дорогая страница приложения, опрос каждые 3 с

**Файлы:** `src/components/AdminCollector.tsx:19` (`POLL_MS = 3000`),
`src/app/api/admin/collector/route.ts:95-104`, `:229-252`, `src/lib/admin.ts:64-68`

Один тик опроса запускает:

1. `SELECT DISTINCT symbol, exchange FROM "ObRollupBucket"` — **Seq Scan**
   (подтверждено `EXPLAIN`), таблица растёт до 30 дней истории. Дважды: в
   `listFeeds()` роута и в `getFeedFreshness()` из `lib/admin.ts`.
2. `getFeedFreshness()` — плюс по одному `max(t) FROM "ObSnapshot"` на фид.
3. `tableStats` — **3 таблицы × N фидов** запросов вида
   `(SELECT count(*) ... WHERE t > now() - '1 minute') , (SELECT max(t) ... )`
   по партиционированным `ObTrade`/`ObFootprint`/`ObBigTrade` **без ограничения
   по времени во второй половине** — `max(t)` обходит все партиции.

При 4 фидах это ~15 запросов, из них два полных скана, каждые 3 секунды всё
время, пока вкладка админки открыта.

**Что делать:**

- список фидов — не из данных, а из конфигурации: `CollectorConfig` (десяток

- `max(t)` ограничить окном: `WHERE t > now() - interval '1 hour'` — свежесть

- поднять `POLL_MS` до 10–15 с (свежесть фида — это 90-секундный порог

- завести общий кэш ответа с TTL ~5 с через `createRouteCache` — админов может
  быть несколько.

## ⚪ D5. `PageView` — снято: таблицы такого размера на проде нет

**Пункт закрыт замером, а не сделан.** Ниже — что было предложено и почему
отменено; оставляю целиком, чтобы к этому не возвращались заново.

**Что предполагалось.** `PageView` пишется на каждый просмотр страницы, несёт
шесть индексов, а чистится массовым `deleteMany` по `ts < cutoff`. В схеме она
названа «самой быстрорастущей таблицей приложения», отсюда и предложение:
партиционировать по `ts` с `DROP PARTITION` вместо DELETE, плюс свернуть семь
проходов `rollupTraffic` в один через `GROUPING SETS`.

**Замер на стенде** (синтетический миллион строк за 120 дней, те же шесть
индексов — локальная `PageView` для замера негодна, в ней 623 строки):

| | результат |
|---|---|
| семь проходов свёртки | 768 мс |
| один проход `GROUPING SETS` | 325 мс |
| сверка результатов | 0 расхождений, включая NULL в группируемой колонке |
| `DELETE` 250 тыс. строк | 624 мс, освободилось **0 байт**, 25% строк стали мёртвыми |
| `VACUUM` после него | 928 мс |
| `DROP PARTITION` тех же 250 тыс. строк | **9.3 мс**, освободилось 70 МБ сразу |

То есть механика подтвердилась: партиционирование быстрее чистки в 167 раз и
единственное реально возвращает диск, а свёртка одним проходом вдвое дешевле и
даёт побайтово те же цифры.

**Почему всё равно не делаем.** Панель «Здоровье БД» на проде (2026-08-29,
суммарно 27.31 GB) показывает в топе таблиц только `Ob*` и `FxCandle`.
`PageView` в первые полтора десятка не попадает вовсе — то есть она меньше
самой мелкой показанной таблицы (33.7 МБ). При таком объёме:

* свёртка идёт раз в сутки из крона — экономия 0.44 с в день, это ничто;
* партиционирование переписывает живую таблицу ради десятков мегабайт.

**Когда вернуться.** Партиционирование начинает окупаться примерно от сотен
тысяч строк — при 90-дневном хранении это порядка тысячи просмотров в сутки.
Проверять так:

```sql
SELECT count(*), pg_size_pretty(pg_total_relation_size('"PageView"')) FROM "PageView";
```

**Ошибка процесса, которую стоит запомнить.** В первой редакции отчёта пункт
был помечен 🟠 на основании комментария в схеме («самая быстрорастущая
таблица»), без проверки фактического размера на проде. Формулировка в коде
описывала темп роста относительно других таблиц, а не абсолютный масштаб.
Приоритет по описанию, а не по замеру — так делать нельзя.

## 🟠 P1. `/api/orderflow/candles`: TTL кэша меньше интервала опроса — 100% промахов

**Файлы:** `src/app/api/orderflow/candles/route.ts:20` (`TTL_MS = 3000`),
`src/app/dashboard/orderflow/page.tsx:814` (`LIVE_CANDLES_MS = 5000`)

Клиент опрашивает каждые **5 с**, кэш живёт **3 с**. Попадания не бывает
никогда. Каждый промах — это `fetchOrderflowCandles` с `live=true`, то есть:

1. чтение до 800 свечей из `ObCandle`;
2. **синхронный HTTP-запрос к Binance** за формирующейся свечой;
3. `INSERT ... ON CONFLICT DO UPDATE` в `ObCandle` — **запись в БД на GET-запросе**.

Собственный комментарий в `lib/orderflow.ts:97` измеряет цену пункта 2:
**366 мс из ~400 мс**. То есть 90% времени ответа — поход на биржу, и он
повторяется каждые 5 секунд на каждую открытую вкладку.

**Что делать:**

- поднять `TTL_MS` минимум до `LIVE_CANDLES_MS` (лучше 6000, с запасом на джиттер) —
  это сразу схлопывает нагрузку от нескольких вкладок в один пересчёт;
- перенести добор формирующейся свечи в коллектор. Он и так ходит за свечами
  (`fetchAndStoreCandles`, раз в 60 с) — для символов, по которым собирается
  стакан, достаточно отдельного таймера на 5 с только для `limit=2`. Тогда роут
  становится чистым чтением из БД, без сети и без записи.

## 🟠 P3. `/api/forex`: три одинаковых запроса, промах кэша на каждом опросе, полное окно каждые 3 с

**Файлы:** `src/app/api/forex/route.ts:80-172`, `src/app/dashboard/forex/ForexView.tsx:428`

Три функции — `fetchCandles`, `computeBA`, `computeDelta` — выполняют
**побайтово одинаковый** `prisma.fxCandle.findMany` с тем же
`symbol/exchange/interval/t`-диапазоном, каждая тянет до 2000 строк, и потом
считают из них разное:

```ts
const [candles, ba, deltaRes] = await Promise.all([
  fetchCandles(symbol, range, fromMs, toMs),
  computeBA(symbol, fromMs, toMs, sourceInterval),
  computeDelta(symbol, fromMs, toMs, sourceInterval),
```

Плюс `TTL_MS = 3000` при опросе клиента ровно раз в 3000 мс — снова гарантированные
промахи. Плюс на каждый опрос уезжает **всё окно целиком**: 2000 свечей ×
(6 чисел) + 2000 точек B/A + 2000 delta + 2000 CVD ≈ 30 тыс. чисел, порядка

Для сравнения, на `/dashboard/orderflow` эта задача уже решена правильно:

```ts
const rows = await prisma.fxCandle.findMany({

const candles = AGGREGATE_FROM[range] ? aggregateCandles(rows, TF_MS[range]) : rows;
```

плюс поднять TTL выше интервала опроса, плюс разделить опрос на «хвост» (`?since=`,

## ⚪ P6. Аналитика — снято: писать пачками нечего

**Пункт закрыт замером, а не сделан.**

**Что предполагалось.** Схема «middleware (edge) → HTTP на localhost → route
(node) → Prisma» удваивает число HTTP-запросов к единственному процессу Node, а
`recordHit` делает две записи: `pageView.create` и `visitSession.upsert`, из них
первая — в таблицу с шестью индексами. Предлагалось буферизовать события и
писать пачками (`createMany` раз в 2 секунды или по 50 событий).

**Почему не делаем.** Тот же замер, что закрыл D5. Строка `PageView` со всеми
индексами весит ~370 байт (стенд: 1 млн строк = 370 МБ). На проде таблица не
попадает даже в полтора десятка крупнейших, то есть меньше 33.7 МБ:

```
потолок строк:        < 95 500
при ретеншне 90 сут:  < 1 060 просмотров в сутки
                      < 0.74 записи в минуту
```

Буфер, который почти всегда сбрасывает одну строку, — это не оптимизация, а
лишняя сложность плюс окно потери событий при перезапуске контейнера.

**Когда вернуться.** Если посещаемость вырастет до десятков тысяч просмотров в

## 🟡 F1. Оба языковых словаря едут в браузер — но размен не окупается

**Файлы:** `src/lib/i18n/dictionaries.ts`, `src/lib/i18n/core.ts:3`,
`src/lib/i18n/provider.tsx:5`

`provider.tsx` — клиентский компонент, он тянет `translate` из `core.ts`, а тот
статически импортирует **весь** `dictionaries`. Значит каждый посетитель,
включая анонима на лендинге, скачивает и парсит оба языка.

**Замер (gzip, по исходнику):**

| | исходник | gzip |
|---|---|---|
| оба словаря | 235.5 КБ | **65.6 КБ** |
| только en | 95.6 КБ | 29.5 КБ |
| только ru | 139.9 КБ | 36.4 КБ |

То есть на первой загрузке лишними едут ~30 КБ сжатого. Величина заметная.

**Почему не исправлено.** Стандартный способ в App Router — отдавать активный
словарь пропсом из серверного layout. Но тогда он уезжает из кэшируемого
JS-чанка в RSC-payload: первому заходу это ничего не даёт (те же ~30 КБ), а
возвращающемуся посетителю делает ХУЖЕ — чанк браузер держит в кэше, payload
приходит заново. Загрузить нужный язык динамическим импортом на клиенте нельзя
без риска рассинхрона гидрации: строки нужны синхронно на первом кадре.

Рабочий вариант есть — отдавать словарь отдельным кэшируемым по URL скриптом
(`/i18n/ru.js`), — но это блокирующий тег и своя машинерия ради 30 КБ. Решение
отложено осознанно, а не забыто; если браться, то за этот вариант.

## 🟠 F2. `I18nProvider` — побочный эффект в рендере и новый контекст каждый раз

**Файл:** `src/lib/i18n/provider.tsx:36-58`

```tsx
setFormatLocale(locale);      // ← мутация модульного состояния ПРЯМО В РЕНДЕРЕ
setFormatTimezone(timezone);

const t: T = (key, vars) => translate(locale, key, vars);   // ← новая функция каждый рендер

return (
  <I18nContext.Provider value={{ locale, t, setLocale, timezone, setTimezone }}>  // ← новый объект каждый рендер
```

Два дефекта:

1. Побочный эффект во время рендера ломается при конкурентном рендеринге и в
   StrictMode (двойной вызов) — React это прямо запрещает.
2. `value` — литерал объекта, `t` — новая замыкание. Провайдер обёрнут вокруг
   **всего кабинета**, поэтому любой его ре-рендер перерисовывает всех
   потребителей контекста, а их десятки.

```tsx
useEffect(() => { setFormatLocale(locale); setFormatTimezone(timezone); }, [locale, timezone]);
const t = useCallback<T>((key, vars) => translate(locale, key, vars), [locale]);
const value = useMemo(() => ({ locale, t, setLocale, timezone, setTimezone }), [locale, t, timezone]);
```

## Фактическая картина на проде (2026-08-29, всего 27.31 GB)

| таблица | размер | доля | что это |
|---|---|---|---|
| `ObSnapshot` (4 партиции) | 13.83 GB | 51% | сырые снапшоты, скользящий буфер на 3 суток |
| `ObSnapshotRollup` | 8.96 GB | 33% | минутный слой истории, 40.4 млн строк, 30 суток |
| `ObCandle` | 1.30 GB | 5% | свечи, 5.33 млн строк |
| `ObSnapshotRollupH` | 268 МБ | 1% | часовой слой, хранится вечно |
| `ObRollupBucket` | 54 МБ | — | счётчики минутных бакетов, 172 330 строк |
| всё остальное | ~2.9 GB | 10% | футпринт, лента, прикладные таблицы |

Три таблицы — 89% базы. Отсюда же видно, почему D3 стоил так дорого до правки:
разведка каскада делала два полных прохода по `ObSnapshotRollup`, то есть
**~18 GB чтения каждые пять минут** (около 5 TB в сутки) при `shared_buffers=1GB`.

## Ограничение владельца: историю не удаляем

Свечи и агрегаты лимитных блоков нужны для будущего анализа рынка, поэтому
ретеншн `ObCandle`, `ObSnapshotRollup*` и `ObRollupBucket*` **не сокращаем** —
предложения «минутный слой 30 → 10 суток» и подобные сняты.

Уточнение к границе понятий: `ObSnapshot` (13.83 GB) историей не является — это
буфер, который и сейчас удаляется целиком каждые трое суток (`DROP PARTITION`).
Rollup строится не из него, а накоплением в памяти коллектора, поэтому длина
этого буфера на сохранность истории не влияет вовсе. Держать его трое суток
осмысленно ровно для одного: возможности посмотреть стакан по-тиково с шагом
2 с за последние дни. Это решение владельца, а не техническая необходимость.

## Что можно сжать без потери единой строки

**Дёшево — неиспользуемые индексы `(symbol, bucket)`.** Локально `idx_scan` у
части из них ноль (см. D6). На проде самый крупный — `ObSnapshotRollup_symbol_bucket_idx`,
по пропорции порядка 1.3 GB. Обслуживает только выборку `exchange="all"`.
Проверять перед удалением:

```sql
SELECT c.relname, s.idx_scan, pg_size_pretty(pg_relation_size(c.oid))
FROM pg_stat_user_indexes s JOIN pg_class c ON c.oid = s.indexrelid
WHERE c.relname LIKE '%symbol_bucket%' ORDER BY pg_relation_size(c.oid) DESC;
```

**Крупно — убрать текст из каждой строки.** `ObSnapshotRollup`: 40.4 млн строк
на 8.96 GB, ~238 байт на строку. В каждой лежит `exchange` текстом
(«binance-futures», 16 байт) и `symbol` («BTCUSDT», 8 байт) — при том что бирж
четыре, а символов единицы. Оба поля входят ещё и в первичный ключ, то есть
дублируются в индексе.

Замена на `smallint` + справочник по одной этой таблице: ~800 МБ в куче,
~800 МБ в PK, ~240 МБ в индексе `(symbol, bucket)` — итого **~1.8 GB**. То же
применимо к `ObSnapshot`, `ObCandle` (там ещё `interval` текстом), `ObFootprint`,
`ObTrade`; суммарно по базе ориентировочно **4–6 GB при полном сохранении всех
данных**.

Это не пункт аудита, а отдельный проект: меняется схема, коллектор, все запросы,
плюс миграция 27 GB. Браться стоит, только если поджимает диск.

Что уже сделано хорошо и трогать не надо:

- каскад минута → час → сутки для стакана и футпринта (сжатие ~400× на дневном
  уровне) — идея правильная, ломает её только баг B1;
- партиционирование `Ob*` по суткам с `DROP PARTITION` вместо `DELETE`;
- BRIN вместо btree по `bucket` на rollup-таблицах;
- локальное хранение обложек новостей в webp (1.5 МБ → ~20 КБ) и отдельная
  таблица `NewsImage`, чтобы байты не ездили при чтении ленты;
- предагрегаты `Trade`, `TradeHourly`, `ObLatestBook` вместо пересчёта на лету;
- `compress: true` в Next + `sharedCacheHeaders` для публичных данных.

# 9. Что в проекте сделано хорошо

Чтобы список выше не создавал ложного впечатления — базовая инженерия здесь
сильно выше среднего:

- **Шифрование секретов**: AES-256-GCM с authTag, ключ из env с проверкой длины
  (`lib/crypto.ts`) — без нареканий.
- **TOTP**: собственная реализация RFC 6238 с `timingSafeEqual`, окном ±1 и
  раздельными лимитами по IP и по пользователю. Корректна.
- **Отзыв сессий** через `tokenVersion` с кэшем и служебным значением
  `DELETED_USER_VERSION = -1` — вдумчиво, включая разбор конкретного бага в
  комментарии.
- **Валидация загружаемых картинок по magic bytes**, а не по `Content-Type`.
- **Backup-роут**: allowlist действий, регэксп на имя файла, урезанный `env` для
  дочернего процесса, `spawn` без shell — сделано правильно.
- **OAuth**: `state` в httpOnly-cookie, сверка в callback, `redirectLocal` для
  обхода проблемы с реверс-прокси.
- **Security-заголовки**: CSP, `frame-ancestors 'none'`, HSTS, `nosniff`,
  `Referrer-Policy`, `Permissions-Policy`.
- **Middleware**: отдельный рубеж для `/api/admin` (закрывает известную дыру),
  корректный демо-режим с гардом на изменяющие методы.
- **Кэши** (`routeCache` с дедупликацией «в полёте» и stale-while-revalidate,
  `statsCache` с версионированием и порогом по размеру) — грамотно и с явными
  границами памяти.
- **Комментарии**: почти каждое неочевидное решение объяснено вместе с историей
  «почему не наоборот». Это редкость и сильно ускорило аудит.
- **2735 тестов, все зелёные.** Пробел не в количестве, а в покрытии границ:
  ни один тест не проверяет выравнивание границ каскада, ownership в
  `/api/trade-fills` и поведение flush при ошибке БД.
