`src/app/api/admin/backup/route.js`, `.../backup/upload/route.ts`,
`.../backup/file-info/route.ts` — **не проверяют ни сессию, ни права админа**.
Доступны кому угодно из интернета.

### Почему защита не сработала

Middleware (`src/middleware.ts`) закрывает пути так:

```ts
if (pathname.startsWith("/dashboard") || pathname.startsWith("/admin")) { … }
```

Путь `/api/admin/backup` начинается с `/api`, а **не** с `/admin`, поэтому под
эту проверку не попадает. Роль админа проверяется в `/admin/layout.tsx` (для
страниц) и вызовом `getAdminSession()` внутри каждого API-роута — но в этих трёх
файлах такого вызова нет.

Отдельно: `route.js` — единственный роут проекта на JavaScript. Любая проверка
или соглашение, ищущее `route.ts`, его пропускает (**мой первый скан тоже его
пропустил** — нашёл только два роута из трёх, третий всплыл при обстреле).

### Подтверждённая цепочка атаки

Всё выполнено анонимно, без единой куки:

```
1. POST /api/admin/backup/upload   (multipart, файл evil.sql)
   → HTTP 200 {"success":true,"name":"evil.sql","size":77}
   → файл реально записан в backup/tmp/

2. GET /api/admin/backup?action=list
   → HTTP 200, выдаёт АБСОЛЮТНЫЕ пути на диске сервера:
     {"path":"/Users/…/statstrade/backup/tmp/evil.sql", …}

3. POST /api/admin/backup {"action":"restore","file":"evil.sql"}
   → HTTP 200 {"operationId":"…"}
   → GET ?operationId=… показал логи: скрипт РЕАЛЬНО запустился
     ("Starting restore", далее вывод db-backup-functions.sh)

4. DELETE /api/admin/backup?file=evil.sql
   → HTTP 200 {"success":true} — файл удалён
```

Шаг 3 — самое опасное. Тело запроса попадает сюда:

```js
const args = [action];                     // action — из тела запроса
if (file) args.push(join(TMP_DIR, file));
spawn('bash', [BACKUP_SCRIPT, ...args], { cwd: PROJECT_ROOT, env: process.env });
```

`spawn` без `shell: true` не интерпретирует метасимволы, поэтому прямой
command injection не проходит. Но атакующий **свободно выбирает команду
скрипта**. Скрипт сам перечислил свои команды в ответе на невалидный `restore`:

```
export_full, export_data_only, export_analytics,
import_with_dedup <file>, import_clean <file>   ← «полная замена базы»
create_basic_dump, show_help
```

То есть шаги 1 + 3 с `action=import_clean` = **полная подмена продовой базы
файлом атакующего**. `import_clean` я намеренно **не запускал** — это уничтожило
бы твою локальную БД; механизм доказан безопасными командами.

Дополнительно `env: process.env` передаёт дочернему процессу все секреты
(`DATABASE_URL`, `ENCRYPTION_KEY`, `JWT_SECRET`), а `export_full` пишет дамп в
каталог, который потом читается через `?action=list` и отдаётся.

### Что чинить

1. В начало **каждого** из трёх роутов (и всех методов `route.js`: GET/POST/DELETE)
   добавить `getAdminSession()` → `notFound()` при отсутствии прав.
2. Продублировать проверку в middleware: закрыть `/api/admin/:path*` требованием
   валидной сессии — чтобы забытый гард в новом роуте не означал открытую дверь.
3. `route.js` → `route.ts` (тогда его видят типы и любые проверки по `route.ts`).
4. `action` принимать только из белого списка команд, а не любую строку.
5. Не передавать `process.env` целиком в `spawn` — только нужные переменные.

> - **не больше 500 рисунков на пользователя**;

>   иначе они копились вечно;

> тело запроса читается отдельно — раньше и битый JSON, и превышение размера
> тела отдавались пользователю как **500**, теперь как **400**.
>
> **Перепроверено на живом сервере и БД:** 1 млн точек (32 МБ) → 400; 10 000
> точек → 400; `label` 100 000 символов → 400; `symbol` 50 000 → 400;
> `color: "<img src=x onerror=...>"` → 400; `price: 1e400` → 400; неверное число
> точек → 400; 501-й рисунок → `drawing limit reached (500)`. При этом все
> четыре инструмента, которые шлёт UI, создаются, обновляются и удаляются
> нормально, а PUT по чужому id → отказ. Тесты: 31 в `drawings` (было 21),
> 18 в `favorites` (было 13), полный прогон **1815 / 249 зелёные**,
> `tsc` чист, `next build` проходит.

### Нет ограничений на объём пользовательского ввода

**Рисунки на графиках** (`/api/orderflow/drawings`, `/api/forex/drawings`) —
единственные пользовательские роуты вообще без zod-схемы. `validateInput()`
в `src/lib/drawings.ts` проверяет тип инструмента (белый список) и структуру
точек, но **не ограничивает**:

- число точек в массиве — можно прислать миллион;
- длину `label`, `color`, `fillColor` — произвольные строки;
- длину `symbol` / `exchange` — только «непустое»;
- количество рисунков на пользователя — не ограничено.

Итог: любой залогиненный пользователь может неограниченно раздувать БД.

**Размер тела запроса** (подтверждено): 10 МБ проходит, 15 МБ отвергается —
где-то между ними лимит Next. Через открытый upload (см. критичную находку)
это анонимная запись 10 МБ на диск за запрос. За nginx стоит
`client_max_body_size 20m`, отдельного лимита у приложения нет.

**Чинить:** zod-схемы для обоих drawings-роутов (`points` ≤ N, длины строк,
`color` по regex `#rrggbb`), лимит рисунков на пользователя, явный предел
размера тела для роутов, которые не принимают файлы.

## ✅ ПРОВЕРЕНО И СДЕЛАНО ХОРОШО

Это не «не смотрел» — это проверено и претензий нет.

**SQL-инъекции — не найдено.** `Prisma.raw` (единственный способ вставить
строку в запрос без параметризации) не используется **нигде**. Четыре
`$queryRawUnsafe`/`$executeRawUnsafe` интерполируют только имена таблиц из
`as const`-массивов, а значения передают параметрами `$1`/`$2`. Все остальные
сырые запросы — теговые шаблоны `Prisma.sql`, то есть параметризованы.
Сортировка в `/api/trades` берётся из белого списка, а не из строки запроса.

**Загрузка файлов — сделано правильно.** `src/lib/imageValidation.ts` определяет
тип по **magic bytes**, а не по `Content-Type` от клиента; разрешены только
png/jpeg/webp/gif. SVG и HTML (классический вектор XSS через «картинку»)
отсекаются. Лимит 10 МБ проверяется до чтения файла в память. Сами файлы уходят
в облако пользователя, а не на наш диск.

**Прокси картинок — без SSRF.** `/api/trade-images/view` не принимает URL:
ищет запись по паре (userId, tradeKey), путь к файлу наружу не отдаёт.
Остальные `fetch` на сервере идут по URL, собранным из констант; символ/биржа
предварительно очищаются регуляркой.

**Админка по прямому URL — закрыта** (подтверждено): `/admin`, `/admin/users`,
`/admin/backup` без сессии → `307` на `/login`; с сессией не-админа layout
отдаёт `404` (а не `403` — не раскрывает существование раздела). Все 26
API-роутов в `/api/admin/**` на TypeScript проверяют права; дыра только в трёх
файлах бэкапа.

**XSS** — `dangerouslySetInnerHTML` не используется ни разу; CSP задан в
`next.config.ts` (`script-src` ограничен, `frame-ancestors 'none'`,
`object-src 'none'`), плюс HSTS, `nosniff`, `Referrer-Policy`.

**Аутентификация** — JWT в httpOnly/SameSite=Lax cookie, скользящее продление,
`tokenVersion` отзывает все сессии при смене пароля, 2FA (TOTP) с шифрованием
секрета AES-256-GCM, rate limit на входе/регистрации/2FA/поддержке/загрузке,
Turnstile-капча на регистрации, политика пароля (длина + регистры + цифра +
спецсимвол). Ключи бирж шифруются AES-256-GCM.

**Cron-эндпоинт** — только по `Authorization: Bearer $CRON_SECRET`, секрет из
query-параметра убран осознанно (чтобы не оседал в логах прокси).

— admin gating happens at the infra/proxy layer». Никакого гейта на уровне
