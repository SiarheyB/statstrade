# TradeStats — заметки для Claude

## ⚠️ Деплой: домашний мини-сервер, НЕ Vercel

Проект **НЕ деплоится на Vercel**. С 2026-06-27 — **самохостинг на домашнем
мини-ПК (Debian 12)**, весь стек в Docker.

- **Стек:** `docker-compose.prod.yml` = `db` (postgres:16) + `app` (Next.js) +
  `collector` (сбор стакана) + `watchtower` (авто-обновление).
- **Сборка образов:** GitHub Actions (`.github/workflows/deploy.yml`) на **push в
  `main`** → пушит в GHCR (`ghcr.io/siarheyb/statstrade-{app,collector}`).
  Слабый сервер сам НЕ собирает — только тянет образы.
- **Авто-деплой:** `watchtower` каждые ~120с подхватывает новые образы из GHCR и
  перезапускает контейнеры. Push в `main` → через пару минут уже на сервере.
- **Миграции БД:** применяет контейнер `app` при старте — CMD
  `prisma migrate deploy` (см. `Dockerfile`). Миграции пишем вручную в
  `prisma/migrations/` (Docker локально не держим).
- **Правки `docker-compose.prod.yml` / `.env`** watchtower НЕ подхватывает — на
  сервере нужен ручной `git pull && docker compose -f docker-compose.prod.yml up -d`.
- **Публичный доступ:** Tailscale Funnel (`sudo tailscale funnel --bg 3000`).
- **Полный гайд:** `docs/SELF_HOSTING.md`.
- Репозиторий: **`SiarheyB/statstrade`**.

> Примечание: раздел «Деплой на VPS» в `README.md` — устаревший ручной вариант;
> актуальный прод — самохостинг через Docker/GHCR/watchtower выше.

## Форекс — Dukascopy как основной источник

- `collector/forex/` собирает **все** инструменты (и пары, и металлы) из
  **Dukascopy** (`collector/forex/dukascopy.mjs`) — без ключей. Finnhub WS и
  Twelve Data остались только как резерв.
- **Резерв поднимается сам** (`collector/forex/fallback.mjs`): несколько полностью
  неудачных циклов опроса подряд (`FX_DUKASCOPY_FAIL_CYCLES`, по умолчанию 4) —
  включается Finnhub WS по валютным парам, первый успешный ответ Dukascopy его
  гасит. Металлов у Finnhub нет: `FX_DUKASCOPY_SYMBOLS` — это список того, что
  резерв подхватить НЕ может.
- **Twelve Data по умолчанию выключен** (`FX_TWELVEDATA_ENABLED=1`, чтобы
  включить): историю по всем парам теперь приносит Dukascopy, а бесплатных
  800 запросов/сутки на все пары × таймфреймы не хватало (был перерасход).
- Ключ Dukascopy не нужен, но **обязательны заголовки `User-Agent` и `Referer`** —
  без них приходит HTTP 200 с пустым телом (выглядит как блокировка по гео,
  хотя дело не в ней).
- **Грабли:** бары 1h/1d/1w Dukascopy отдаёт только ЗАКРЫТЫЕ — текущий
  (формирующийся) бар достраивается из минуток в `refreshFormingBucket()`.
  4h не запрашивается вовсе: у Dukascopy он выровнен по UTC-полуночи, а у нас
  сетка сдвинута на час (`bucketStart`, наследие Twelve Data) — собираем из 1h.
- На **закрытом рынке** (пятница 21:00 → воскресенье 22:00 UTC) опрос идёт раз
  в 5 минут вместо 15 секунд, счётчик сбоев резерва не растёт, а админка вместо
  тревоги «пары не обновляются» показывает «рынок закрыт»
  (`src/lib/forexMarket.ts` и его копия в `collector/forex/fallback.mjs` —
  коллектор отдельный сервис и `src/` не видит).
- `exchange="finnhub"` в `FxCandle` — **исторический тег одного логического
  ряда, а не имя провайдера**: под ним лежат данные всех источников, включая
  золото. Приложение фильтрует именно по этому значению, менять его нельзя без
  миграции данных.
- 1m хранится отдельно и короче остальных ТФ (`FX_M1_RETENTION_DAYS`, 30 дней):
  1440 свечей в сутки на инструмент против 288 у 5m.

## Карта ордеров (orderflow)

- `collector/` — отдельный long-running сервис: пишет снапшоты стакана, ленту
  сделок, footprint и крупные сделки в Postgres.
- **Производительность:** heatmap и B/A читают предагрегированные **rollup-таблицы**
  (`ObSnapshotRollup` / `ObRollupBucket`, минутные бакеты), которые наполняет
  коллектор, — а не миллионы сырых `ObSnapshot`. Сырые снапшоты держатся коротко
  (`OB_RETENTION_DAYS` → `cfg.retentionDays`, по умолчанию 7 дней), сделки/футпринт/
  крупные сделки — отдельно (`OB_TRADE_RETENTION_DAYS`), rollup — дольше
  (`ROLLUP_RETENTION_DAYS`, не задан в `docker-compose.prod.yml` → дефолт 365 дней).

## Посещаемость сайта (`/admin/traffic`)

- Свой счётчик, не внешняя аналитика: считает **на сервере** (`src/middleware.ts`
  → `lib/traffic/track.ts` → внутренний POST на `/api/analytics/collect`), поэтому
  видит и посетителей с блокировщиками, и роботов. Браузерный маячок
  (`components/TrafficBeacon.tsx`) — второй слой: подтверждает «JS исполнился»
  (`jsConfirmed`) и досылает переходы внутри приложения.
- **Грабли Next 16:** заголовки `RSC: 1` / `Next-Router-Prefetch: 1` до middleware
  НЕ доходят — фреймворк снимает их раньше. Отличать документ от служебного
  запроса роутера приходится по `Sec-Fetch-Dest`/`Sec-Fetch-Mode`; иначе каждая
  предзагрузка ссылки считалась бы просмотром (см. `pageViewKind`).
- **matcher middleware сплошной** (все пути, кроме статики) — раньше был точечный
  список. Гарды от этого не изменились: они по-прежнему смотрят на префикс пути.
- Приёмник дёргается по `http://localhost:$PORT` (НЕ `127.0.0.1`: `next dev` на
  macOS слушает только IPv6, запрос на IPv4 виснет).
- В БД не хранится ни одного IP: `visitorId` — cookie `ts_vid` либо хэш IP+UA с
  солью (`ANALYTICS_SALT`, по умолчанию `JWT_SECRET`).
- **Оповещения** (`lib/traffic/alerts.ts`) пишутся в `ErrorLog` — это и есть канал
  уведомлений админки (бейдж на «Логах»). Быстрые проверки гоняются на приёме
  событий не чаще раза в 15 минут, суточная — в кроне.
- Сканерские пути (`/wp-login.php`, `/.env`, …) middleware обрывает коротким
  404 ДО рендера, но событие в статистику пишет — иначе всплеск не увидеть.
- Страна берётся только из заголовков CDN (`CF-IPCountry` и аналоги); своей
  GeoIP-базы в приложении нет и не планируется.
- `robots.txt` / `sitemap.xml` — динамические (`app/robots.ts`, `app/sitemap.ts`),
  адрес сайта из заголовков (`lib/siteUrl.ts`), `/share/<токен>` закрыт от
  индексации намеренно.
- `PageView` — самая быстрорастущая таблица; чистит её крон
  `/api/cron/analytics` (свёртка в `TrafficDaily` + удаление старше
  `ANALYTICS_RETENTION_DAYS`, дефолт 90). Без этой задачи в crontab таблица
  растёт бесконечно — см. docs/SELF_HOSTING.md §9.3.

## i18n / часовой пояс — сквозной паттерн

- Язык (`src/lib/i18n/`) и таймзона (`src/lib/timezone.ts`) хранятся **одинаково**:
  cookie (`ts_locale` / `ts_timezone`) + `I18nProvider`/`useI18n()` на клиенте,
  `getLocale()`/`getTimezone()` на сервере. Никакого поля в модели `User` — это
  осознанное решение, не персистентность между устройствами.
- **Даты/время форматируются в двух режимах:** большинство мест идёт через
  `fmtDate()` (`src/lib/format.ts`) — там таймзона учтена централизованно. Но
  canvas-графики (orderflow, liqmap) и календарь/econcal рисуют подписи
  вручную (`getHours()`/`getDate()` и т.п., не `toLocaleString`) — для них
  таймзона применяется через `zonedParts()`/`zonedDateToUtcMs()` из
  `lib/timezone.ts`, а не через `fmtDate`. При добавлении нового
  времени/даты в UI — сначала проверь, не нужен ли этот сдвиг.

## 🛑 Что ломает прод

- Неправильная команда в `Dockerfile` (`npm ci` вместо `npm install` может сломать сборку из‑за рассинхрону lockfile).
- Ошибки в `package.json` (например, пробелы перед зависимостью) вызывают `EJSONPARSE` при `npm install`.
- При обновлении риск‑менеджера забываем, что лимиты хранятся в `RiskProfile`, а не в `User`.
- `getNetStopsCount` считает «чистые стопы»: выигрыш (+3R) перекрывает два стопа (−1R каждый), поэтому в окне риска может показываться 0.
- При правке `docker‑compose.prod.yml` или `.env` watchtower НЕ перезапускает сервер автоматически — нужен ручной `git pull && docker compose up -d`.
