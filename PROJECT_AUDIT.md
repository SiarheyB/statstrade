## 1.2 Блок A — статистика сделок (самое ценное для UI)

### A1. [x] `/api/risk` — регресс, чинить первым — **ВЫПОЛНЕНО**

Было:
```ts
// src/app/api/risk/route.ts:21
const fills = await prisma.fill.findMany({ where: { account: { userId: user.userId } } });
const trades = reconstructTrades(inputs);   // ← реконструкция ВСЕЙ истории
```

Таблица `Trade` для этого и заведена (`prisma/schema.prisma:170`). Роут просто не
перевели. Плюс `findMany` без `select` тянул все колонки филлов.

Шаг 1 (`src/app/api/risk/route.ts`) — уход от реконструкции:
- чтение `prisma.trade.findMany` с `select` ровно под нужные поля;
- окно `exitTime >= начало текущего года (UTC)` — самый широкий лимит риск-
  менеджера это `year`, всё старше на статус не влияет;
- `where.accountId: { in: [...] }` по уже загруженным аккаунтам вместо join
  через `account: { userId }`;
- при нуле аккаунтов запрос вообще не выполняется;
- добавлен `ensureAccountTrades()` — одноразовый бэкафилл для legacy-аккаунтов
  (иначе у них риск показал бы ноль), тот же путь, что в `/api/stats`.

Шаг 2 (пункт 8 плана) — уход и от построчного чтения сделок:
- `computeAccountRisk` принимает `RiskDay[]` (строки `TradeDaily`) вместо
  `RiskTrade[]`; тип `RiskTrade` удалён;
- роут читает дневные агрегаты — ≤365 строк на аккаунт в окне года вместо
  всех сделок за год;
- `getNetStopsCount` (`lib/riskManager.ts`) вместо выборки сделок делает один
  `prisma.tradeDaily.aggregate({ _sum: { netPnl } })` — суммирование целиком
  в Postgres.

Почему числа не поехали: границы всех окон риск-менеджера проходят по границам
суток UTC (`periodStart()`), а `TradeDaily` нарезан ровно по ним же; для счётчика
стопов `Σ(netPnl)/rAmount == Σ(netPnl/rAmount)`, для «чистого счёта» без 1R —
`Σ(losses − wins)` по дням равно поштучному подсчёту (безубыточные не входят ни
в `wins`, ни в `losses` — как и раньше).

Тесты: кейсы `computeAccountRisk` остались описанными в терминах СДЕЛОК, но
сворачиваются хелпером `toDays()`, повторяющим SQL из `daily.ts`, — все 27
ожидаемых чисел не изменились. Плюс тест «читаем агрегаты, а не филлы и не
сделки, и только с начала года». Побочно: `tsc`-ошибок стало 148 вместо 170.

### A2. [x] Таблица `TradeDaily` — дневные агрегаты — **СЛОЙ ДАННЫХ ГОТОВ**

Сделано: модель + рукописная миграция `20260806200000_add_trade_daily`
(сверена с `prisma migrate diff --from-empty` — совпадает байт в байт),
модуль `src/lib/analytics/daily.ts`, бэкафилл при старте, тесты.

Принятые решения:
- **День = дата `exitTime` в UTC.** Совпадает с `Metrics.daily` и с периодным
  календарём риск-менеджера (`periodStart()` — там тоже `Date.UTC`), поэтому
  суммы сходятся с этими экранами точно.
- Колонки `exitTime` имеют тип `TIMESTAMP(3)` **без** таймзоны и хранят UTC —
  значит `"exitTime"::date` и есть UTC-дата. `AT TIME ZONE` применять НЕЛЬЗЯ:
  он превращает значение в `timestamptz`, и приведение к `date` поедет по
  таймзоне сессии Postgres.
- Агрегат считается целиком в Postgres (`DELETE` + `INSERT…SELECT` в одной
  транзакции), строки в Node не переносятся. Crypto (`Trade`) и импортированные
  (`ImportedTrade`) сворачиваются в одни и те же строки; соответствия полей
  (`fees = commission`, вывод `result` из знака `netPnl`) повторяют `/api/stats`.
- Пересборка одного дня (`rebuildTradeDailyForDay`) — для правки одной сделки,
  чтобы не перетряхивать всю историю аккаунта на каждое сохранение аннотации.
- Точки пересчёта не заводились новые: вызовы встроены в
  `recomputeRRForAccount` / `recomputeRRForTradeKey`, а через них автоматически
  покрыты все пять существующих триггеров (rebuild сделок, правка stopLoss,
  смена риск-профиля, импорт отчёта, демо-данные). `winR/lossR` складываются
  из уже сохранённого `rr`, поэтому пересборка идёт строго ПОСЛЕ его записи.

**Читателей пока нет — это осознанно.** Бэкафилл стартует фоново при запуске
контейнера; если бы потребитель приехал тем же деплоем, он успел бы отдать нули
до окончания бэкафилла. Поэтому сначала деплоится таблица с наполнением, а
`/api/risk` и дашборд переводятся на неё следующим шагом.

**Ограничение:** «Календарь» бакетит по `entryTime` и в таймзоне пользователя —
другая нарезка, эту таблицу он использовать не может, пока не решён B5.

Ниже — исходное описание задачи.


Закрывает: календарь, `metrics.daily`, `byDayOfWeek`/`byMonth`, тренд 30д,
`getNetStopsCount`, месячную сводку, PnL-хитмап.

```prisma
model TradeDaily {
  accountId String
  day       DateTime @db.Date   // календарный день в UTC
  trades    Int      @default(0)
  wins      Int      @default(0)
  losses    Int      @default(0)
  netPnl    Float    @default(0)
  grossProfit Float  @default(0)
  grossLoss   Float  @default(0)
  fees      Float    @default(0)
  volume    Float    @default(0)
  winR      Float    @default(0)   // Σ положительных rr
  lossR     Float    @default(0)   // Σ отрицательных rr
  rTrades   Int      @default(0)   // сколько сделок с посчитанным rr
  account   ExchangeAccount @relation(fields: [accountId], references: [id], onDelete: Cascade)

  @@id([accountId, day])
  @@index([day])
}
```

Наполнение — **одним SQL**, без выгрузки в Node, в тех же точках, где уже
вызывается `recomputeRRForAccount` (`src/lib/analytics/rr.ts:9-18`):

```sql
INSERT INTO "TradeDaily" (...)
SELECT "accountId", date_trunc('day', "exitTime")::date, COUNT(*), ...
FROM "Trade" WHERE "accountId" = $1
GROUP BY 1, 2
ON CONFLICT ("accountId","day") DO UPDATE SET ...;
```

Точки пересчёта (уже существуют, добавить один вызов):
`materialize.rebuildTradeGroups` / `rebuildAccountTrades`, `/api/annotations` PUT
(меняет stopLoss → rr), `/api/risk/settings` PUT, `/api/accounts/[id]/import`.

**Важный нюанс — таймзона.** Календарь бакетит по `entryTime` в таймзоне
пользователя (`calendar/page.tsx:20`), а `metrics.daily` — по `exitTime` в UTC
(`metrics.ts:284`). Это уже сейчас даёт расхождение цифр между «Календарём» и
графиком daily P&L на дашборде. Варианты:
1. хранить в `TradeDaily` день по UTC, а на сервере отдавать календарь через
   `date_trunc('day', "entryTime" AT TIME ZONE $tz)` — точно и без клиента;
2. решить, что бакетим по одному полю (`exitTime`), и убрать расхождение.

Рекомендация: сделать endpoint `GET /api/calendar?month=…&tz=…&accountId=…`,
который отдаёт готовую сетку 42 ячеек + месячную сводку. Клиент перестаёт
получать сделки вообще (кроме списка выбранного дня — отдельный запрос).

## 1.3 Блок B — MFE/MAE (exit efficiency)

`src/lib/analytics/exitEfficiency.ts` запускается **в браузере**, делает до
`maxTrades` параллельных `GET /api/trade-chart`, каждый из которых ходит в ccxt
за свечами. Результат никуда не сохраняется — следующий клик считает всё заново.

Но MFE/MAE закрытой сделки **неизменны**. Это классический кандидат в БД:

```prisma
model Trade {
  // …
  mfePct      Float?    // максимальный ход в плюс, %
  maePct      Float?    // максимальная просадка, %
  capturedPct Float?    // сколько из движения забрали
  bestPrice   Float?
  mfeAt       DateTime? // когда посчитано (null = ещё не считали)
}
```

Считать фоново после `rebuildTradeGroups` (или отдельным воркером в коллекторе,
чтобы не грузить Next-процесс), пачками, с уважением к рейт-лимитам биржи.
Тогда карточка Exit Efficiency открывается мгновенно и без внешних запросов,
а «худшие сделки» можно показывать прямо в таблице сделок.

## 1.4 Блок C — orderflow (самый горячий контур)

Клиент опрашивает `/api/orderflow` **каждые 3 секунды** (`orderflow/page.tsx:649`),
плюс отдельные эндпоинты divergence / imbalance / absorption / volume-profile
с TTL 12 с. Каждый промах кэша = тяжёлые агрегации по партиционированным таблицам.

### C1. [x] ВЫПОЛНЕНО — `ObTradeRollup` — минутные бакеты ленты

```prisma
model ObTradeRollup {
  symbol   String
  exchange String
  bucket   DateTime @db.Timestamptz(3)  // начало минуты
  buyVol   Float    @default(0)
  sellVol  Float    @default(0)
  trades   Int      @default(0)          // ← реальное число сделок
  @@id([symbol, exchange, bucket])
  @@index([symbol, bucket])
  @@index([bucket])                      // для pruneOld
}
```

Пишет коллектор ровно тем же механизмом, что `ObSnapshotRollup`
(`collector/index.mjs:399-465` — аккумулятор в памяти + flush по границе минуты).
`computeDelta` и `computeSpeedOfTape` переключаются на него; при пустом rollup —
fallback на сырьё, как уже сделано в `computeBA`/`computeOrderflow`.

**Это же чинит баг #8**: сейчас `COUNT(*)` по `ObTrade` считает снапшоты
(коллектор пишет одну агрегированную строку на тик, см. `collector/trades.mjs:29`),
а не сделки. «Скорость ленты» показывает ≈ константу 60/`snapshotMs`.
Нужен реальный счётчик — его же можно добавить и в сырой `ObTrade`.

### C2. `ObFootprintRollup` — footprint по свече

`computeFootprint` каждый раз делает `GROUP BY bucket, price` по сырью для окна
в 400–800 свечей. Коллектор может сразу писать агрегат по фиксированной сетке
(5m — базовый интервал, остальные ТФ складываются из него):

```prisma
model ObFootprintRollup {
  symbol   String
  exchange String
  interval String   // "5m"
  bucket   DateTime @db.Timestamptz(3)
  price    Float
  buyVol   Float @default(0)
  sellVol  Float @default(0)
  @@id([symbol, exchange, interval, bucket, price])
  @@index([symbol, exchange, interval, bucket])
}
```

### C3. `ObLatestBook` — текущий профиль стакана

`src/lib/orderflow.ts:612-622` на каждый запрос выполняет запрос с коррелированным
подзапросом `MAX("t")` по сырому `ObSnapshot` — по сути дважды сканирует окно
ради «последнего снапшота». Коллектор и так держит его в памяти:

```prisma
model ObLatestBook {
  symbol   String
  exchange String
  t        DateTime @db.Timestamptz(3)
  levels   Json     // [{price, bidVol, askVol}]
  mid      Float
  @@id([symbol, exchange])
}
```
Одна строка на пару, `upsert` на каждый тик — дёшево, читается по PK.

### C4. `ObSignal` — дивергенции и абсорбция

Оба детектора детерминированы по закрытым свечам и одинаковы для всех

model ObSignal {

Роуты становятся простыми `SELECT … WHERE t BETWEEN …`.

**🔴 [x] `prisma migrate deploy` не собирал базу с нуля — ИСПРАВЛЕНО**

Воспроизведено дважды на заведомо пустой БД:

```
Applying migration `20260720073840_stattrade`
Applying migration `20260722000000_add_user_levels`
Error: P3018 / 42P07 — ERROR: relation "UserLevel" already exists
```
(успевает создать 66 таблиц и умирает)

**Механизм.** В `_prisma_migrations` у `20260720073840_stattrade` записан
checksum `e3b0c442…b855` — это SHA-256 **пустой строки**. То есть на всех
существующих БД эта миграция применилась пустым файлом, ничего не создав.
Содержимое (включая `CREATE TABLE IF NOT EXISTS "UserLevel"` и `UserDrawing`)
добавили в файл ПОЗЖЕ. Поэтому:

- на существующих БД `UserLevel` создала следующая миграция
  `20260722000000_add_user_levels` — конфликта не было и нет;
- на чистой БД теперь отрабатывают обе, а вторая создаёт таблицу уже **без**
  `IF NOT EXISTS` → падение.

**Что это значит на практике.** Прод и локальные БД, выросшие постепенно, в
порядке — их пересобирать не нужно. Ломается только сценарий «поднять схему с
нуля через `migrate deploy`», а это ровно то, что делает прод-контейнер в
`docker-entrypoint.sh`, то есть путь восстановления после потери диска.

**Обходной путь есть:** `prisma db push` на чистой БД проходит (41 таблица).
Но он НЕ эквивалентен: `Ob*`-таблицы получаются обычными, а не
партиционированными (`relkind='r'` вместо `'p'`), а на партициях завязана
очистка по ретеншну (`DROP PARTITION` вместо `DELETE`).

**Как починено.** `20260720073840_stattrade/migration.sql` возвращён к пустому
виду — к тому, в котором он реально применялся на существующих базах. Обе
таблицы имеют собственные миграции (`20260722000000_add_user_levels`,
`20260722000001_add_user_drawings`), так что содержимое было чистым
дублированием. Рядом положен `README.md` с объяснением, почему файл пустой и
что заполнять его нельзя. Сами дублирующие миграции НЕ трогались — их checksum
не изменился.

Побочный эффект: на базах, где `stattrade` применялась пустой (прод), checksum
теперь снова совпадает — расхождение, описанное выше, устранено.

Проверено: чистая БД → `migrate deploy` → **57/57 применено, 0 ошибок**, все
таблицы на месте, `Ob*` остались партиционированными (на этом держится очистка
по ретеншну через `DROP PARTITION`).

```bash

psql "$DATABASE_URL" -c 'DROP TABLE "UserLevel"; DROP TABLE "UserDrawing";'
# 2. упавшая миграция не применила ничего — помечаем откаченной

```

11. [x] B5 решён; «Календарь» переведён на агрегаты.
    **Решение владельца:** день сделки определяется по `exitTime` (P&L
    фиксируется при закрытии), границы суток — в таймзоне пользователя,
    включая окна риск-менеджера.
    **Сделано:**
    - `TradeDaily` → **`TradeHourly`**. Дневной агрегат в UTC для таймзоны
      пользователя непригоден: один UTC-день попадает на два локальных и
      сложением готовых строк не пересобирается. Часовые бакеты складываются
      в локальные сутки при любом сдвиге, кратном часу — а список таймзон в
      приложении состоит ровно из таких.
    - новый `lib/analytics/periods.ts`: `periodStart`/`periodEnd` принимают
      сдвиг, плюс `bucketByLocalDay` / `sumInPeriod` / `localDayKey`.
      Реализация календаря теперь ровно одна на весь проект.
    - `/api/risk` и `getNetStopsCount` считают окна в tz пользователя; клиент
      передаёт сдвиг (`?tzOffset`), см. `lib/tzParam.ts` и
      `tzOffsetForServer()` в `lib/timezone.ts`. Ключ кэша счётчика стопов
      включает сдвиг — у разных таймзон окна разные.
    **Найдено при этом:** `sumInPeriod` не ограничивал окно сверху и захватывал
    часы позже `now` — в проде незаметно (сделок из будущего нет), но результат
    зависел от того, что вызывающий положил в массив. Добавлена верхняя граница.
    - **`GET /api/calendar`** поверх `TradeHourly`: отдаёт дневную сетку,
      свёрнутую в локальные сутки, список счетов и `latest` (последний торговый
      день — чтобы страница открывалась на месяце последней сделки). Диапазон
      ограничен 70 днями: сетка календаря это максимум 6 недель, более широкий
      запрос вытянул бы всю историю одним вызовом.
    - страница «Календарь» больше **не качает `/api/stats`** (то есть всю
      историю сделок) и не бакетит в браузере: дни приходят готовыми, сделки
      выбранного дня — отдельным запросом к `/api/trades` окном локальных суток
      (для этого в `/api/trades` добавлен фильтр `from`/`to` по `exitTime`).
    - день теперь считается по `exitTime` — «Календарь» сошёлся с дашбордом и
      риск-менеджером на многодневных сделках.
    Тестов у страницы не было — добавлены: сетка запрашивается диапазоном в
    42 дня со сдвигом таймзоны, `/api/stats` не дёргается, дневные суммы
    рисуются из ответа, клик по дню запрашивает окно ровно в 24 часа локальных
    суток. Плюс 9 тестов нового эндпоинта.
